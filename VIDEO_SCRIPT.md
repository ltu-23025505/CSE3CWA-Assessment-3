# Video demonstration script (3–5 minutes)

The video is the main evidence that the application is genuinely deployed and working on the public
Internet. **Record the deployed application, not localhost.**

Have these ready before you start:
- The deployed URL open in a browser tab (and **warmed up** — click it a minute or two before recording,
  because free instances sleep after 15 minutes idle)
- A terminal with the cURL commands pre-typed
- A second browser tab on the Render Dashboard — **Overview** and **Environment**

Do **not** show your real JWT, your client secret or your `JWT_SECRET` on screen.

**Target length: about 4:45.** Timings below are a guide; the only hard limit is staying between 3 and
5 minutes.

Show the browser address bar.

> "This is AI Capsule, running on Render at
> `https://cse3cwa-assessment-3-rziz.onrender.com`. It is not localhost — it's a public HTTPS URL on a
> real cloud platform. The app is a React frontend, an Express backend and a SQLite database, all
> served from this one origin."

```bash
curl -i https://cse3cwa-assessment-3-rziz.onrender.com/api/health
```

> "The health endpoint is public so the deployed backend can be checked on its own. It returns
> `{"status":"ok"}` — so the Express backend is live, not just the frontend."

## 0:35 – 1:10 · Both 401 tests, before logging in

```bash
curl -i https://cse3cwa-assessment-3-rziz.onrender.com/api/capsules
```

> "Test one: `GET /api/capsules` with no authentication. It returns `401 Unauthorized` with a JSON
> error body, and no capsule data at all."

```bash
curl -i -H "Cookie: token=fake-token-123" https://cse3cwa-assessment-3-rziz.onrender.com/api/capsules
```

> "Test two: the same request with a fake token in the cookie. Also `401 Unauthorized`. That's the
> important one — it proves the server actually **verifies** the JWT signature rather than just
> checking whether a cookie exists, so a cookie that isn't a valid signed token is rejected."

> "All four CRUD routes use the same middleware — GET, POST, PUT and DELETE are each mounted behind
> it in the source."

---

## 1:10 – 1:40 · GitHub OAuth login

Click **Continue with GitHub**, authorise, land on `/dashboard`.

> "Signing in goes through GitHub. The server sends me there with a random `state` value, GitHub
> returns a one-time code, and the server exchanges that code for my profile. It then signs its
> **own** session token — this is the application's JWT, not GitHub's access token — and stores it in
> a `Secure`, `HttpOnly` cookie called `token`. The dashboard shows my GitHub identity, which came
> from that verified token, not from anything the browser sent."

If the dashboard is empty, say so:

> "The list is empty because there's no seed data — so everything you're about to see is a real
> database write."

---

## 1:40 – 2:50 · Complete CRUD on the deployed app

**CREATE** — click **New capsule**, fill in Project `SmartFarm Irrigation`, title `Debug cloud
deployment`, version `v1`, category `Coding`, usefulness `Good`, tick **Reviewed**, paste a prompt and
a response summary, then **Create capsule**.

> "That's a `POST` to `/api/capsules`, saved with my user id taken from the verified token."

**READ** — reload the page.

> "Reloading re-reads from `/api/capsules`. The record is still there, so this came out of the deployed
> SQLite database, not React state."

**UPDATE** — click **Edit**, change the title to `Debug cloud deployment (fixed)` and usefulness to
`Needs Improvement`, then **Save changes**.

> "A `PUT`, scoped to my user id. One record is updated rather than duplicated."

**DELETE** — click **Delete**, confirm.

> "A `DELETE`. The record is gone and the empty state returns. Every one of those operations was
> limited to records owned by the identity in my signed token — a second GitHub account would see its
> own records only."

Leave one record behind for the marker.

## 2:50 – 3:20 · Cloud configuration, no secrets

Switch to the Render Dashboard.

- **Overview** — service name, region (Singapore), instance type **Free**, and the `*.onrender.com` host.
- **Environment** — the variable **names**: `NODE_VERSION`, `NODE_ENV`, `JWT_SECRET`,
  `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`.

> "These are the environment variables. The secret values are hidden — I'm only showing the names.
> `NODE_ENV=production` is what turns on the `Secure` cookie, and `JWT_SECRET` was generated by Render
> rather than typed by hand. There's deliberately no `DATABASE_PATH`, which is the next point."

- **Events / Logs** — the successful deploy.

---

## 3:20 – 3:50 · Storage, persistence and the limitation

> "Storage is SQLite — one file inside the service directory. There's no database service to
> provision, which keeps this to a single web service.

> The honest limitation is that this is a **free** instance, and free instances have **no persistent
> disk**. The filesystem is ephemeral: the database file is erased whenever the service restarts,
> redeploys, or spins down after fifteen minutes idle. So CRUD works correctly on every visit, but
> records don't survive the instance being recycled — which is why the dashboard can legitimately be
> empty after a cold start. A managed Postgres database would fix both the durability and the
> single-instance limit, at the cost of another service to run and a network round trip per query."

---

## 3:50 – 4:25 · Three problems found and fixed

> "Three problems came up that are worth explaining, because two of them only appear once you deploy.

> **The big one: my first deploy crashed before the app even started.** The log said `GLIBC 2.38 not
> found`, loading sqlite3's prebuilt binary. The package's own release history showed why: the 5.1
> line deliberately keeps its binaries compatible with older Linux by building them on an older image,
> but version 6 dropped that work when it modernised its build — and the project has since been
> archived. Pinning back to 5.1.7 restored a compatible prebuilt binary. That's a dependency-version
> problem, not a code problem, and the fix was one line.

> **The second: the app sits behind Render's proxy, which terminates HTTPS and forwards plain HTTP.**
> Without telling Express to trust that first proxy hop, it refuses to set a `Secure` cookie — and the
> symptom is nasty: the login appears to work, and then every subsequent request returns 401. That's
> why `trust proxy` is set in the server.

> **The third is smaller.** In development the React dev server proxies to Express, and the generated
> config rewrote the `Host` header. Since the OAuth callback URL is derived from the incoming host,
> that would have sent the callback to the wrong origin. Removing that option keeps the callback
> correct on localhost and here."

---

## 4:25 – 4:45 · Wrap up

> "So: a public Render deployment, a public health check, both unauthenticated requests correctly
> rejected, GitHub OAuth issuing the application's own JWT into an HttpOnly cookie, and the full
> create, read, update and delete cycle working against the deployed API with per-user data isolation.
> That's AI Capsule."
